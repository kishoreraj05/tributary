# tributary-engine

A config-driven, plugin-based PySpark engine. Pipeline specs come from YAML, JSON or the API. The engine compiles them, plans them and runs them in batch, streaming or preview mode.

## Commands

| Command | What it does |
|---|---|
| `tributary validate FILE [-e ENV] [--deep]` | Checks the spec schema, references, DAG cycles and the table names used in SQL. `--deep` also checks columns and types with Spark, using empty frames (no data is read), and lets sinks check their options against the data they would get (a Delta merge key the SQL does not produce, a type the existing table will refuse). It runs on the pipeline's own session, like `preview` and `run`, so sources whose schema lives in the data system (a Delta table) are analysed too. |
| `tributary plan FILE [--explain]` | Shows the physical plan (step order, cache points, quality gates) and the chosen Spark resources. `--explain` adds Spark's physical plan of every source and transform, as a run builds them: pushed-down filters, pruned columns and partitions (reads metadata only). |
| `tributary preview FILE --node ID [--limit N] [--sample SRC=path] [--write] [--explain] [--json]` | Shows the rows a node would produce from bounded reads. Sinks are a dry run unless `--write` is given. `--explain` adds Spark's physical plan for the node. |
| `tributary run FILE [-e ENV]` | Runs the pipeline. Streaming pipelines keep running until stopped. |
| `tributary schema-export [-o FILE]` | Writes the JSON Schema of the spec and the component catalog (this is what the UI uses). |
| `tributary list-components` | Lists every registered plugin. |
| `tributary convert A.yaml B.json` | Converts a pipeline between YAML and JSON. |

The same operations are available from Python: `tributary.compile_pipeline / plan / preview / analyze / explain / run / export_schema`.

## How it works

```
document ─▶ compile ─────────────────────────────▶ plan ──────────────────▶ execute
            env vars + secrets, connections,        quality gates spliced,    batch: once
            spec model built from the registry,     fan-out counted,          streaming: per micro-batch
            references / cycles / SQL tables        persist decided,          preview: needed steps only,
                                                    sinks ordered last        bounded reads
```

- **Plugins everywhere.** Sources, transforms, sinks, checks, metrics sinks, schema resolvers and secret providers are all plugins, discovered through entry points (`tributary.<category>s`). The spec model, its JSON Schema and the UI catalog are generated from the registry. Adding a connector never touches engine code.
- **SQL inputs.** Each entry in `inputs` becomes a temp view named by its `as` alias, defaulting to the node id. At compile time `sqlglot` checks that the query is a single SELECT that reads only those aliases or its own CTEs, and suggests the closest name when a table is unknown. Catalog tables must be listed in `allow_catalog_tables`.
- **Quality gates.**
  - **Attaching:** `attach_to` checks a node's output for all of its consumers; `before` checks only what flows into one sink. Sinks keep pointing at the business node, and the planner rewires them through the gate.
  - **One pass:** all checks run in a single aggregate. Row checks become flag columns; dataset checks become aggregate expressions.
  - **Actions:**
    - `fail` raises an error before any sink writes.
    - `drop` filters out failing rows.
    - `quarantine` also writes the failing rows, with a `_dq_failed_checks` column, to `quarantine_sink`.
  - **Results:** one row per check is sent to each entry in `results_sinks` (console, file, JDBC/Postgres, Prometheus Pushgateway).
- **Deequ node.** `type: deequ` wraps one of [Amazon Deequ](https://github.com/awslabs/deequ)'s three runners, chosen with `runner`; each has its own function list and its own output columns:
  - `analysis` (AnalysisRunner): `analyzers` such as `size`, `completeness`, `uniqueness`, `mean`, `approx_quantile`, `histogram`, `pattern_match`, `correlation`, `compliance`; output `entity, instance, name, value` (histograms flattened, one row per bin, like deequ's `successMetricsAsDataFrame`).
  - `verification` (VerificationSuite): `constraints` such as `is_complete`, `is_unique`, `has_size`, `satisfies`, `has_pattern`, `is_contained_in`, `has_mean`, each with a `level` (error/warning); output `check, check_level, check_status, constraint, constraint_status, constraint_message, metric_name, metric_value`, or `output: data` to pass the input on unchanged as a gate. Assertions are comparisons of the metric (`assertion: ">= 0.95"`, `"between 1 and 100"`); predicate constraints default to every row (`== 1`). `fail_on: error` (default) raises before any sink writes when an error-level constraint fails, `warning` also on warning-level ones, `never` only records. Results go to the run summary and, through `results_sinks`, to the metrics sinks a quality block can use (the backend adds its own, so they show in the run's DQ history); previews never fail, they show the results.
  - `suggestion` (ConstraintSuggestionRunner): `rules` such as `default_rules`, `complete_if_complete`, `retain_type`, `non_negative_numbers`, `has_max`; output `column_name, constraint_name, current_value, description, suggesting_rule, rule_description, code_for_constraint`.
  - **Functions and columns:** an entry names a function and the `columns` it applies to (the function is applied to each column; `correlation`, `mutual_information` and the comparisons take exactly two; `is_primary_key` and `are_complete` take them together; `size`, `has_size`, `satisfies`, `compliance` take none). `where` evaluates it on matching rows only. The names are deequ's own, snake-cased; `tributary schema-export` lists every function with the fields it takes.
  - **Type checks:** deequ's preconditions are checked against the input schema before anything runs, with the column and its type in the message: numeric functions (`mean`, `has_min`, `is_in_range`, `is_non_negative` ...) need a numeric column, string functions (`has_pattern`, `min_length`, `contains_email` ...) a string column, comparisons two columns of the same family, and nothing works on arrays, maps or structs. The UI reports these as you type, like unknown columns.
  - **Plumbing:** deequ is driven through Spark's JVM gateway (as PyDeequ does), with assertions as Python callbacks; the jar comes from Maven Central via `spark.jars.packages` on first use. A deequ node reads the node to check directly: it cannot be upstream or downstream of another deequ node (use one node per runner, each on its own branch). A verification gate (`output: data`) is a pass-through for the planner: its input is read by its aggregation and by its consumers, and gets persisted accordingly.
- **Automatic persist.** The planner counts how often each step's output is read. A pass-through gate (observe/fail) counts as one read and also passes its consumers' reads up to its input. A step read twice or more is persisted; a single-reader step is not. You can override this per node with `cache: auto|always|never` and `storage_level`. For drop/quarantine gates, the flagged frame they split is persisted. Cached frames are released when the run or micro-batch ends.
- **Streaming.** A streaming pipeline is one streaming query with `foreachBatch`. Each micro-batch is persisted once, and the whole plan (static lookup sources, transforms, gates and every sink) runs on it. The source is read once per batch no matter how many sinks there are. Sinks get `ctx.batch_id` for idempotent writes.
- **Resources.**
  - AQE and dynamic allocation are always on.
  - `resources: auto` picks an S/M/L/XL profile from the estimated input size (local file listing) and the number of joins and aggregations.
  - Explicit `resources` fields override the profile, and raw `spark_conf` overrides everything.
  - Only the Spark packages of the plugins a pipeline uses are added (for example spark-sql-kafka, spark-avro, the Postgres JDBC driver, the Iceberg runtime, the Delta jars), and so are the session settings they declare (Iceberg's `spark.sql.catalog.*` entries, Delta's session catalog).
- **Iceberg source.** Reads an Iceberg table through a Spark catalog, with the same catalog settings as the sink (so one connection of type `iceberg` serves both). By default the current table; `snapshot_id`, `as_of_timestamp`, `branch` or `tag` read it as it was; `start_snapshot_id` (and `end_snapshot_id`) read only the rows appended after a snapshot, and nothing when nothing was appended; `metadata_table` reads `snapshots`, `refs`, `files`, ... instead, which is how to find the ids. `filter` and `columns` are pushed down into Iceberg's scan (partition and file pruning, column pruning), as are the predicates of downstream SQL in a run. In a streaming pipeline the source is a stream of the table's appends (`stream_from_timestamp` to skip history, `streaming_skip_overwrite_snapshots` / `streaming_skip_delete_snapshots` to get past commits that were not appends, `max_files_per_trigger` / `max_rows_per_trigger` to throttle). Schema changes are picked up on the next read; a declared `schema` pins a fixed set of columns and types instead. [`docs/iceberg-source.md`](../docs/iceberg-source.md) walks through every feature and how to test it; see also [`examples/iceberg_to_parquet.yaml`](../examples/iceberg_to_parquet.yaml) and [`examples/iceberg_stream_to_parquet.yaml`](../examples/iceberg_stream_to_parquet.yaml).
- **Iceberg sink.** Writes to an Iceberg table through a Spark catalog (`catalog_type`: hadoop, hive, rest, glue, jdbc or nessie; the catalog settings usually come from a connection of type `iceberg`). Each type asks only for what it needs: a `warehouse` for hadoop/glue/jdbc/nessie, a `uri` for hive/rest/jdbc/nessie (hive and rest take the warehouse from the service), `credential`/`token` for rest. Modes: `append`, `overwrite`, `overwrite_partitions` (dynamic) and `merge` (upsert on `merge_keys`). The namespace and table are created on first write, with `partition_by` accepting Iceberg transforms (`days(ts)`, `bucket(16, id)`, ...) and `table_properties`. Every commit made through the DataFrame writer carries the run id in its snapshot summary; in streaming, appends are also tagged with the micro-batch id and a replayed batch is skipped, so a restart never duplicates rows. Deep validation checks `merge_keys` and the columns inside the partition transforms against the upstream schema. See [`examples/csv_to_iceberg.yaml`](../examples/csv_to_iceberg.yaml).
- **Elasticsearch sink.** Writes one JSON document per row to an `index` (an alias or data stream works too, and `logs-{country}` or `events-{ts|yyyy.MM.dd}` routes rows by a column) through the official Spark connector (ES-Hadoop), with the cluster settings (`nodes`, `port`, `ssl`, `user`/`password` or `api_key`, `wan_only`) usually coming from a connection of type `elasticsearch`. With an `id_column` the document id is that column's value, so running the pipeline again, or replaying a micro-batch, replaces documents instead of adding copies; without it Elasticsearch generates ids. Modes: `append` (index), `overwrite` (delete the index's documents first; fixed index names only) and `upsert` (update the columns given for documents that exist, add the others). TIMESTAMP and DATE columns are sent as ISO-8601 text by default so a new index maps them as dates (`timestamp_format: epoch_millis` keeps the connector's numbers for an index whose mapping already says `date`). `auto_create_index: false` fails instead of letting Elasticsearch create the index with a dynamic mapping; `write_options` passes any other `es.*` setting (routing, batch sizes, proxies). Deep validation checks `id_column` and the columns the index pattern reads against the upstream schema, flags the types the connector cannot send (decimals, `timestamp_ntz`), and, with the sink's credentials, asks the cluster about the target: a value that cannot fit the existing mapping (a struct where a number is mapped, a boolean where a date is), new columns on a `dynamic: strict` (refused) or `dynamic: false` (stored, not searchable) mapping, an alias with no write index, a missing index while `auto_create_index` is off. See [`examples/csv_to_elasticsearch.yaml`](../examples/csv_to_elasticsearch.yaml) and, for running and testing it locally, [`deploy/elasticsearch/README.md`](../deploy/elasticsearch/README.md).
  - **When the cluster pushes back.** Rows go out in bulk requests of `batch_size_entries` documents per task, and the requests are independent: the ones before a failure are indexed (partial success). Documents a shard rejects with 429 are resent in place, only those, after `retry_wait` and up to `retry_count` times (`-1`: until they get in); they are never indexed twice. A whole request refused with 429 (the coordinating node's queue is full), a document the mapping refuses for good, or retries that run out fail the task; Spark's task retry or a re-run then writes the partition again, which is only harmless with an `id_column`. `rejected_documents: skip` logs documents the mapping refuses (`tributary.elasticsearch.rejected` in the run log) and carries on without them.
  - **Rollover (ILM).** Write to the alias, create the first index with `is_write_index: true` yourself (ILM's rollover action needs it) and set `auto_create_index: false`, or the first write creates a plain index by the alias' name that can never roll over. The switch is atomic on the cluster, so a rollover in the middle of a write loses nothing: each bulk request lands whole in whichever index is the write index at that moment. Idempotency by id holds within one index only: a document written again after a rollover (a replayed micro-batch, an upsert) goes to the new write index next to its old copy, so rollover suits append-only streams. Data streams take `write_options: { es.write.operation: create }` and a `@timestamp` column.
- **Elasticsearch source.** Reads an index, alias or pattern through the ES-Hadoop connector: one partition per shard, `_source` fields as columns, the index mapping as schema (`array_fields` names the fields that hold arrays, which mappings do not say). `query` limits what is read (a URI query `?q=...` or a Query DSL body) and `fields` which fields, `include_metadata` adds a `_metadata` map with the document `_index`/`_id`. A `schema` block on the node selects and casts those columns, and lets the editor know them without asking the cluster. The cluster settings (`nodes`, `user`/`password`, `ssl`, `wan_only`, on by default so Docker and cloud clusters work) usually come from a connection of type `elasticsearch`. Batch only: the connector has no streaming reader, so in a streaming pipeline an index is a static lookup source. See [`examples/elasticsearch_to_mongodb.yaml`](../examples/elasticsearch_to_mongodb.yaml). With `use_dummy_data` on, the node stands in for the index: it emits the documents of `dummy_data` (a JSON array, 100 at most, typed as an index mapping would type them, a document's `_id` becoming `_metadata._id`) in previews and runs alike, needs no cluster settings and no connector jar, and never contacts Elasticsearch, so a pipeline can be drawn and tested before the index exists; switch it off to read the real index. See [`examples/elasticsearch_dummy_data.yaml`](../examples/elasticsearch_dummy_data.yaml).
- **Delta source.** Reads a Delta Lake table at a `path` (local, s3a://, gs://, abfss://, hdfs://). The table carries its own schema, so the `schema:` block is optional: without one, deep validation and the editor take the columns from the table's log; with one, the source selects those columns cast to the declared types (a contract that holds as the table evolves, and lets a pipeline be drawn before its producer has created the table). In batch, `version` or `timestamp` read a past version (time travel). In streaming, the table as it is and then every commit; `starting_version` / `starting_timestamp` move the start (`latest` = new commits only, for a query that keeps running), `on_changes` says what to do with commits that update or delete rows (Delta streams appends: `fail`, the default, `ignore_deletes`, `ignore_changes` re-emits rewritten files, `skip_commits`), `max_files_per_trigger` bounds a micro-batch. `change_feed` reads the table's change data feed instead of its rows (`_change_type`, `_commit_version`, `_commit_timestamp` columns; the table needs `delta.enableChangeDataFeed`, which the Delta sink sets through `write_options` when it creates the table): in batch from `starting_version`/`starting_timestamp`, in streaming as a change stream. Previews are bounded batch reads (a change feed without a start samples the last commit). Reads need the same session catalog as writes, which the source sets itself. `use_dummy_data` makes the node pretend: `dummy_data` (a JSON array of at most 100 records, edited as JSON in the UI) is what it produces in batch, preview and streaming, and the table is never contacted, so a pipeline can be drawn and tested before the table exists or away from the lake. See [`examples/delta_to_parquet.yaml`](../examples/delta_to_parquet.yaml) (batch, time travel) and [`examples/delta_changes_to_delta.yaml`](../examples/delta_changes_to_delta.yaml) (a change feed keeping a second table current, deletes included).
- **Delta sink.** Writes a Delta Lake table at a `path` (local, s3a://, gs://, abfss://, hdfs://). Modes: `append`, `overwrite`, `overwrite_partitions` (dynamic) and `merge` (upsert on `merge_keys`; `update_condition` limits which matches are updated, e.g. `s.updated_at > t.updated_at`, `insert_condition` which new rows are inserted, and `delete_condition` turns a match into a delete for change feeds; `t` is the table row, `s` the incoming one). The table is created on first write with `partition_by`; schema enforcement is Delta's (new or differently typed columns are refused; cast in the SQL transform), `schema_evolution` adds new columns on append, overwrite and merge; `write_options` go to the Delta writer (`delta.*` ones become table properties when the table is created). In streaming, appends and overwrites carry the pipeline and micro-batch ids as Delta's `txnAppId`/`txnVersion`, so a replayed batch is skipped (turn `skip_replayed_batches` off when replaying from a fresh checkpoint into an existing table). The `delta-spark` Python package is installed with the engine; the jar version follows it. Deep validation (what the editor runs while you draw) checks `merge_keys`, `partition_by` and the `s.`/`t.` references of the conditions against the upstream schema, and against the existing table's columns and types, so these fail in the form rather than in a micro-batch. See [`examples/csv_to_delta.yaml`](../examples/csv_to_delta.yaml) (batch) and [`examples/file_stream_to_delta.yaml`](../examples/file_stream_to_delta.yaml) (streaming upserts, one commit per micro-batch).
- **MongoDB source.** Reads a collection through the official MongoDB Spark Connector (`connection_uri`, `database`, `collection`; optional `pipeline`, an aggregation pipeline run on the server, and `read_options` for the connector's other settings). Without a `schema:` block the connector infers the columns from a sample of the collection; a `ddl`/`static` schema pins them. With a declared schema, `on_malformed` decides what happens to a document whose field does not fit its type (`null` the field, `drop` the document, or `fail` the run; without a schema the connector reads a mixed-type field as string). With **`use_dummy_data: true`** the node never connects: it hands the documents in `dummy_data` (a JSON array of up to 100 documents, or a YAML list) to the downstream nodes as a collection holding them would, so a pipeline can be drawn, tested and run before the real collection is reachable. The connection fields are then not needed (and the connector jar is not fetched); the columns come from the declared schema or are inferred from the records like JSON (nested documents become structs). See [`examples/mongodb_to_parquet.yaml`](../examples/mongodb_to_parquet.yaml).
- **MongoDB sink.** Writes a collection through the official MongoDB Spark Connector: every row becomes a document (structs become embedded documents, arrays stay arrays, timestamps become dates, decimals Decimal128), and a column named `_id` becomes the document id. The server is given as a `connection_uri` (`mongodb://` or `mongodb+srv://`, with client settings such as `replicaSet`, `authSource` or `tls` as query parameters); `username`/`password` are spliced into it, so a connection of type `mongodb` can keep the password encrypted. Modes: `append` (insert), `overwrite` (drop the collection, then insert) and `upsert` (match on `merge_keys`; `on_match: replace` swaps the whole document for the row, `on_match: update` only sets the row's columns and keeps the document's other fields; unmatched rows are inserted). **Idempotency:** appends get a deterministic document id (`deterministic_ids`, on by default: sha1 of the pipeline, the micro-batch or run, and the row, with genuine duplicates within a batch kept distinct) and are written as upserts, so a micro-batch replayed after a crash, or a write retried after a partial failure, rewrites the same documents instead of adding copies; `upsert` on `merge_keys` is idempotent by nature and is how a *batch* pipeline can be re-run over the same data without duplicates (ids of batch appends are scoped by run, so re-running an append pipeline appends again, on purpose). **Resiliency:** transient failures (server unreachable, connection dropped, primary stepping down, retryable server codes) are retried with exponential backoff (`retries`, `retry_backoff_seconds`); the retry is only attempted when the write is idempotent, so a plain append without deterministic ids fails fast instead of risking copies. A running stream therefore rides out an outage shorter than the retry budget without the query failing; the driver's own `serverSelectionTimeoutMS`/`retryWrites` in the URI still apply underneath. **Schema:** documents are schemaless, so new columns simply appear in new documents (`on_match: update` adds them to existing ones, `replace` swaps the whole document); `ignore_null_values` leaves null columns out, `write_options` takes any other connector option (`writeConcern.w`, `convertJson`, ...). Deep validation checks `merge_keys` against the upstream schema, flags column names MongoDB refuses (dots, a leading `$`), and samples the existing collection (with a short timeout) to catch type drift: a column whose type family changed (int → string, double → string, ...) is reported, and a drifted merge key is flagged because upserts on it would stop matching and duplicate documents. The connector jar is fetched on first use, like the Iceberg runtime. See [`examples/csv_to_mongodb.yaml`](../examples/csv_to_mongodb.yaml).
- **REST API source** (`rest_api`, batch). Calls an endpoint on the driver and turns the records of the JSON it returns into a DataFrame, parsed by Spark's JSON reader (so the columns are inferred, or declared with the node's `schema:` block or `parsing.recordSchema`). `endpoint` holds the `url`, `method`, static `headers`, `queryParams` and `body`, the timeout and the retries (429 and 5xx are retried with exponential backoff, honouring `Retry-After`). `parsing` says what the response looks like: `responseType` (`JSONArray` for `[{...}, {...}]`, `JSONObject` for `{"data": [...], "status": 200}`, `JSONLines` for NDJSON), `recordExtractionPath` (a JSONPath to the records, e.g. `$.data.semesters`; `$.a.b`, `$['a']`, `$[0]` and `$[*]` are supported) and `explodeArray` (one row per array element, or one row per response). `pagination` follows page-number or offset parameters until a page comes back short, empty or `maxPages` is reached; previews stop as soon as they have enough rows. Authentication is `authType` bearer / basic / api_key with `token`, `username`/`password` and `apiKeyHeader`, kept flat so a connection of type `rest_api` can provide them (and a `baseUrl`) per environment. See [`examples/rest_api_to_parquet.yaml`](../examples/rest_api_to_parquet.yaml).
- **REST API enrichment** (`rest_api_enrichment`, a transform). The DataFrame-driven mode of the REST source: one call per row of its input (`dynamicInput.inputStrategy: DataFrameDriven`; `inputDataFrameRef` names the input when there are several), with the row's columns mapped into the request by `parameterMapping`: `pathParams` fill `{name}` placeholders in the URL, `queryParams` add query string parameters and `bodyTemplate` is a JSON body whose `${column}` placeholders are replaced (a value that is exactly one placeholder keeps the column's type). The records of each response are exploded next to the row that produced them (rows whose response has no records are kept with nulls); `includeInputColumns`, `responseColumnPrefix` and `onError` (`fail` or `null`) shape the output. With `bulkRequestSupport`, `bulkBatchSize` rows go into one call (`${column}` then expands to the list of the batch's values, comma-separated in the URL) and `bulkResponseMatch` says which record field and input column match the records back to their rows. `concurrency` is physical: the input is repartitioned to `maxConcurrentCalls` partitions, each a Spark task with one keep-alive session (`connectionPoolSize` connections) paced by a token bucket at `rateLimitPerExecutor` calls per second, so the cluster-wide rate is at most the product of the two. The response columns come from `parsing.recordSchema` when declared, otherwise they are inferred from the responses (cached so the API is called once); deep validation, which runs without data, needs the schema or dummy records. Previews call the API only for the rows they show. The node can name a `connection` of type `rest_api`. See [`examples/rest_api_enrichment.yaml`](../examples/rest_api_enrichment.yaml).
- **Dummy data.** Both REST plugins take `useDummyData` and `dummyData`, a JSON array of up to 100 records typed into the node. With `useDummyData` on, the node only pretends to be the API: it never connects to it (no endpoint is even needed) and hands the dump to the downstream nodes, so the rest of the pipeline can be drawn, tested and run before the API is ready; the enrichment transform then "returns" the dump for every row. With it off, the records still tell deep validation the columns when nothing else does.
- **Placeholders.** `${env.NAME}` and `${secret:PATH}` are resolved when the spec is compiled. A bare `${name}` is left for the plugin owning the field to fill at runtime (the REST body template reads it as a column), and a bare name that is also a variable is reported as a probable `${env.name}` typo.
- **Hudi source.** Reads a Hudi table at `<base_path>/<database>/<table>` with the Hudi Spark data source; `base_path` usually comes from a connection of type `hudi`, the same one the sink uses (its metastore sync settings are accepted and ignored: reading goes through storage). `query_type` is `snapshot` (the table as it is, or as it was at `as_of_instant`: an instant, a timestamp or a date), `read_optimized` (merge-on-read base files only, without the log files written since the last compaction) or `incremental` (the rows changed by the commits after `begin_instant`, up to `end_instant`; `begin_instant` is an instant as in `_hoodie_commit_time`, a timestamp, a date or `earliest`). With a `checkpoint_location`, each batch run reads the commits since the previous successful run: the read is pinned to the latest commit present when it starts, and that commit is recorded only once every sink has written (a failed run or a preview records nothing), so a scheduled pipeline needs no `since` bookkeeping; `begin_instant` then only applies to the first run. Settings of another query type are refused rather than ignored (`as_of_instant` with an incremental read, `begin_instant` with a snapshot), a `cdc` read of a table that does not record changes is refused, and a `read_optimized` read of a copy-on-write table is its snapshot (logged). Rows deleted by the sink's `delete` operation or by Hudi's `_hoodie_is_deleted` marker are gone from snapshot and latest-state reads and appear as `op: d` in the change feed. A downstream filter on a partition column prunes partitions before files are listed; `hoodie.datasource.read.incr.path.glob` in `read_options` restricts an incremental read to some partitions, and `hoodie.enable.data.skipping` uses the metadata table's column statistics where the writer maintains them. Reads follow the table's schema as it evolves: rows written before a column was added read as null in it, widened types apply to every row, the change feed parses old and new rows into the latest columns, time travel shows the schema of that time, and a `schema` block pins what flows downstream; a running stream keeps the schema it started with until restarted. `incremental_format: cdc` turns an incremental read into a change feed, one row per change with `op` (i/u/d), `ts_ms` and the row `before` and `after` as structs of the table's columns, for tables written with `hoodie.table.cdc.enabled=true`. Hudi's `_hoodie_*` columns are dropped unless `include_metadata_columns` is on (keep `_hoodie_commit_time` to record where a run stopped); a `schema` block on the node selects and casts exactly the columns it names instead. In a streaming pipeline the table is read as a stream of its commits, each micro-batch holding the rows changed by new commits, from `start_offset` (`earliest`, `latest` or an instant) when there is no checkpoint yet; previews show a snapshot. Any other `hoodie.*` reader setting goes in `read_options`. Reading needs no Kryo, only the bundle. See [`examples/hudi_to_parquet.yaml`](../examples/hudi_to_parquet.yaml).
- **Hudi sink.** Writes a Hudi table at `<base_path>/<database>/<table>` with the Hudi Spark data source; `base_path` and the optional metastore sync (`catalog_sync`: hms, jdbc or glue, with `catalog_uri` where one is needed) usually come from a connection of type `hudi`. Operations: `upsert` (on `record_key`, the row with the largest `precombine_field` winning, against stored rows too), `insert`, `bulk_insert`, `insert_overwrite` (the partitions present in the data), `insert_overwrite_table` and `delete`; `table_type` is copy-on-write or merge-on-read, `partition_by` lists the partition columns (Hive-style directories by default), and any other `hoodie.*` setting goes in `write_options`. Keys are unique within a partition unless `global_index` is on (then a row whose partition value changes moves instead of being duplicated). `schema_evolution` says what to do when the data's columns differ from the table's: `add_columns` (the default: new columns and widened types are taken in, a batch missing a column is rejected), `reconcile` (missing columns written as null), `drop_columns` (also dropped from the table) or `strict` (the write is refused before it starts, naming the differences). The table is created on first write; its type, record key and partitioning are fixed from then on, and a sink configured differently is refused with a message saying what differs. Hudi refuses null record keys, so put a `not_null` gate with `drop` or `quarantine` in front of a keyed sink when the data may have them. A boolean `_hoodie_is_deleted` column in the data is Hudi's soft-delete marker: on upsert, rows where it is true delete their key instead of updating it (the change feed reports them as deletes). Every commit carries the run id in its metadata; in streaming, commits are also tagged with the micro-batch id and a replayed batch is skipped (looking past any inline compaction or clustering that followed the write), so a restart never duplicates rows even with `insert`. See [`examples/csv_to_hudi.yaml`](../examples/csv_to_hudi.yaml).

## Known limits (v0.1)

- Streaming uses foreachBatch with exactly one stream source. Stateful streaming operations across micro-batches (windowed aggregations with watermarks, stream-stream joins) are not supported yet. Static sources are re-read on every micro-batch.
- Size estimation only covers local paths. Remote and streaming sources default to profile M.
- The REST API source reads on the driver (one request at a time, pages in sequence), which is what bounded APIs need; very large collections are better exposed through a paginated enrichment over a driving frame of page numbers. Its JSONPath is the subset listed above (no filters, no recursive descent). `rateLimitPerExecutor` paces each task; tasks of the same executor do not share a bucket. The Python `requests` package must be installed on the executors.
- The Kafka source (JSON values) and the Postgres and Prometheus metrics sinks were checked by hand against the `deploy/docker-compose.yml` stack. Automated tests for them don't exist yet, and the Avro/Schema Registry path hasn't been run.
- In the Schema Registry resolver, only Avro is supported (JSON Schema and Protobuf are not yet).
- The Elasticsearch sink is tested against a single node without security (`deploy/docker-compose.yml`'s `elasticsearch` service; the tests skip when no cluster answers at `TRIBUTARY_TEST_ES_URL`, `http://localhost:9200` by default). TLS, basic auth and API keys are just connector settings (`es.net.*`) and have not been run against a secured cluster. The connector (`elasticsearch-spark-30`, 8.13.2 by default, `TRIBUTARY_ELASTICSEARCH_VERSION` picks another) serialises decimals and `timestamp_ntz` columns not at all and nested timestamps as epoch milliseconds; `overwrite` deletes the index's documents one bulk request at a time rather than dropping the index, so mappings survive. Rollover is tested with the `_rollover` API, which is what ILM calls; ILM policies and data streams are not in the test distribution and have not been run.
- The MongoDB source and sink are tested against a plain standalone server (`docker compose up -d mongodb`, no auth; the tests skip when no server is reachable at `TRIBUTARY_TEST_MONGODB_URI`, default `mongodb://localhost:27017`). Replica sets, Atlas (`mongodb+srv://`) and authentication only differ in the URI and have not been run. The connector version defaults to 10.5.0 (`TRIBUTARY_MONGODB_CONNECTOR_VERSION` selects another 10.x release). The source reads in batch only (change streams are not wired up), and without a declared schema its dummy data is typed by JSON inference, so ISO timestamps stay strings. Resiliency is tested by cutting a TCP proxy in front of the server (`FlakyProxy` in the tests); replica-set failovers are covered by the same retry path through the driver's error codes but have not been run against a real replica set. The sink's type-drift check compares a sample of the collection, so a type that only appears in unsampled documents is not seen.
- The Elasticsearch source is tested against a single-node Elasticsearch 8 on localhost (the tests skip when it is not listening; `deploy/docker-compose.yml` starts it). `TRIBUTARY_ES_HADOOP_VERSION` (default 8.13.2, the last ES-Hadoop release on Maven Central; it reads Elasticsearch 7 and 8) selects the connector version. Elasticsearch is read in batch only, and the connector reads a field as a scalar unless it is listed in `array_fields`.
- The Delta source and sink are tested on local disk. They do not enable Delta's SQL extension, for the same reason as Iceberg; they only need Delta's session catalog (`spark.sql.catalog.spark_catalog`), which they set on the session they run in. Add `spark.sql.extensions: io.delta.sql.DeltaSparkSessionExtension` to `runtime.spark_conf` for Delta SQL (`MERGE INTO`, `DESCRIBE HISTORY`, `VACUUM`) or the `replaceWhere` writer option, which Delta implements through the extension. Tables are addressed by path; registering them in a metastore is not supported yet. A Delta source stream is one Delta streaming query like any other: several commits can land in one micro-batch (reduce to the last change per key in SQL before a merge sink, as `examples/delta_changes_to_delta.yaml` does), and `starting_version: latest` belongs to a query that keeps running (with `available_now` and nothing to process, no offset is checkpointed and the next run resolves `latest` again).
- The Hudi source and sink are tested against tables on local disk with Hudi 0.15.0 (the tests fetch the Spark bundle from Maven Central once and skip when offline); the same tests pass with `TRIBUTARY_HUDI_VERSION=1.0.2`. Hive metastore, HiveServer2 and Glue sync only add writer settings (and, for Glue, the `hudi-aws-bundle` jar), but they have not been run. Hudi requires `spark.serializer=org.apache.spark.serializer.KryoSerializer`, a static setting the sink declares and the engine applies when it builds a session (the backend's shared preview session too, for every pipeline); a session created elsewhere without it is refused with a clear error. Hudi's SQL extension, `HoodieCatalog` and Kryo registrator are not enabled, for the same reason as Iceberg's extensions: add them in `runtime.spark_conf` if you need Spark SQL DDL/DML on Hudi tables. Incremental reads are served from the files the commits in range wrote; when `begin_instant` is older than the table's active timeline (those commits were archived), Hudi scans the whole table and keeps the rows whose latest commit is in range instead, so a row changed again after `end_instant` is not part of such a window. `earliest` with `latest_state` is read as a snapshot (as of `end_instant` when given): the same data, by a path that also merges a merge-on-read table's log files, which the fallback scan does not. On the 1.x line the source asks for Hudi's version-6 incremental relation and stream source (`hoodie.datasource.read.incr.table.version=6`, `hoodie.datasource.read.streaming.table.version=6`): 1.x's own ones make `begin_instant` and a `start_offset` instant inclusive of a commit's completion time, and in 1.0.2 an open-ended incremental read through them also returns rows of commits outside the range that share a file with changed rows; the version-6 ones read the same way as 0.x. On Hudi 0.x a stream ignores `incremental_format: cdc` and delivers the latest state of the changed rows.
- The Iceberg source and sink are tested against a Hadoop catalog on local disk (the tests fetch the Iceberg runtime from Maven Central once and skip when offline). Hive, REST, Glue, JDBC and Nessie catalogs only differ in configuration, but they have not been run; Glue, JDBC and Nessie also need their own jars (`runtime.spark_conf: { spark.jars.packages: ... }`). `merge` commits go through SQL and so do not carry the run id tag.
- Streaming from Iceberg replays appends only, along the main branch: `snapshot_id`, `as_of_timestamp`, `branch`, `tag` and the incremental bounds are refused for the stream source (Iceberg would silently ignore them). On Iceberg runtimes before 1.10 the throttles `max_files_per_trigger` / `max_rows_per_trigger` only work with the `processing_time` trigger; with `available_now` the runtime would stall the stream after the first files, so the source refuses that combination. Changelog reads (updates and deletes as rows) are not supported.
- The deequ node needs a classic Spark session (it calls deequ's Scala API through Py4J and the JVM calls back into Python for assertions), so it does not run over Spark Connect. It exposes deequ's analyzers, checks and suggestion rules, not its row-level results, metrics repository, anomaly detection or KLL sketches; failing rows cannot be dropped or quarantined by it (a quality block does that). Deequ 2.0.7-spark-3.5 is built for Spark 3.5 and Java 8+; `TRIBUTARY_DEEQU_VERSION` must name a release matching the Spark minor version.
- The Iceberg runtime defaults to 1.6.1, the last release that runs on Java 8; `TRIBUTARY_ICEBERG_VERSION` selects another one (1.10.1 is tested, Java 11+). Iceberg's SQL extensions (`CALL` procedures, `ALTER TABLE ... ADD PARTITION FIELD`, branches) are not enabled by default because they load Iceberg into every session state, including the shared preview session; add `spark.sql.extensions: org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions` to `runtime.spark_conf` if you need them. The sink itself does not: Spark 3.5 runs `MERGE INTO` on Iceberg tables natively.
